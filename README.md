# Secure Examination-Paper Exchange Using Python

A runnable educational demonstration of sender-authenticated encrypted file exchange. Two simulated users operate from separate folders on one computer. The project uses Python 3.11+, `cryptography`, RSA-3072, AES-256-GCM, RSA-OAEP-SHA256 and RSA-PSS-SHA256.

## Architecture

`src/key_manager.py` handles encrypted private-key storage; `sender.py` builds and signs packages; `package_manager.py` validates JSON and canonical bytes; `receiver.py` verifies before unwrapping/decrypting and atomically releases plaintext; `cli.py` supplies commands. The `.secpkg` format carries metadata, wrapped session key, nonce, ciphertext, tag and signature as Base64 JSON.

## Workshop workflow

1. Generate independent keys, using separate strong passwords when prompted:
   `python -m src.cli generate-keys`
2. The command copies sender public key into `recipient_folder/trusted_keys`. In a real exchange, compare its fingerprint over a separate trusted channel. Ensure sender has recipient public key at `recipient_folder/keys/recipient_public.pem` (generated by step 1).
3. Copy `sample_data/examination_paper.txt` to `sender_folder/input/examination_paper.txt` (the provided sample is already there).
4. `python -m src.cli encrypt --input sender_folder/input/examination_paper.txt`
5. Simulate the untrusted channel by copying `sender_folder/outbox/examination_paper.secpkg` to `recipient_folder/inbox/`.
6. `python -m src.cli verify --package recipient_folder/inbox/examination_paper.secpkg`
7. `python -m src.cli decrypt --package recipient_folder/inbox/examination_paper.secpkg`
8. Compare input and output bytes. The output name comes from sanitized untrusted metadata, and existing files are not overwritten.
9. Run `python -m pytest -v` for attack and reliability cases.

The sender and recipient share a computer for the demonstration, but their private keys stay in distinct folders and the sender's key is never used by the recipient. This setup models roles; it is not isolation from a computer administrator or malware.

## CLI examples

Illustrative output: `Keys generated; sender public key copied to recipient trusted_keys. Verify fingerprints out of band.` Successful encryption reports the package path. `verify` only checks the signature; it never decrypts. `decrypt` verifies first and only writes after AES-GCM authentication succeeds. Use `--base PATH` to change the project root; encrypt also accepts `--output`, decrypt accepts `--output-dir`.

## Package and security design

See [docs/security_design.md](docs/security_design.md) for schema details, exact signed/AAD bytes, threat boundaries and production considerations. [docs/sequence_diagram.mmd](docs/sequence_diagram.mmd) contains the sequence flow.

The signature is RSA-PSS over compact, sorted-key UTF-8 JSON of the complete package except the `signature` property. AES-GCM AAD is compact, sorted-key UTF-8 JSON of the metadata object. Metadata and all encrypted fields are therefore signed; metadata is also GCM authenticated. Binary fields are canonical Base64. Supported metadata has a strict allowlist. Package size is capped at 25 MiB; input at 20 MiB.

## Tests and results

Run `python -m pytest -v`. The suite covers authorized transfer, ordinary and re-signed ciphertext alteration, metadata/signature changes, wrong keys, randomization and malformed package cases. See `results/test_results.txt`; it is marked as not executed in the authoring environment because dependencies were unavailable there. Do not treat expected outcomes as executed results.

## Limitations and troubleshooting

This workshop does not provide key revocation, replay prevention, trusted timestamping, authorization policy, endpoint security, availability, audit controls, or protection from compromised machines. Wrong passwords, absent key files, malformed packages, and existing output filenames produce errors. Keep real keys out of source control and verify public-key fingerprints through an independent trusted channel. Never use workshop keys for real examinations.
